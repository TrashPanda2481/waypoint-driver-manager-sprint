The path

Six steps, start to end. Two moved this sprint. Two have not moved at all.

The walking skeleton written on day 3 named the whole path in its ugliest honest form and marked which parts were real. Steps 1 and 2 were gaps then, running on a mock backend because nothing had touched Windows. They are proven now. Steps 5 and 6 were gaps then and are gaps now.

  1. A technician opens a terminal on a Windows machine and runs waypoint scan. Way in.
    Proven
  2. Devices print grouped by PnP Setup Class into Missing, Problem and Upgrade available. Was: mock backend and Linux parity only.
    Proven
  3. waypoint plan prints each candidate as a diff card: installed against candidate, plus the source and its hash.
    Built
  4. waypoint apply prints the exact commands and the diffs, and applies nothing. Dry run is the default. Installing takes an explicit flag.
    Built
  5. waypoint apply --apply takes a verified restore point, exports the current driver, and installs one driver. Written in full. Has never run against a live driver.
    Gap
  6. One result line in the append-only audit log, naming the restore point, the backup path, and the single command that undoes it. Way out. Depends on step 5.
    Gap

What is still faked

The riskiest part has not moved

Day 2 circled one bet: that a reversible, verified install and rollback chain is a real thing and not just a promise. The whole margin over “an SDI reskin” rests on it. Four sessions later it has exactly as much real-hardware evidence behind it as it had then, which is none.

The restore point has never been created. pnputil has never installed anything. The rollback has never been fired. Every part of that chain is written and tested against a mock; none of it has run on a machine that could break.

  • Windows Update sourcing is unreachable. Native AOT disables built-in COM, so the catalog source built on day 4 cannot run in the configuration this ships in. It needs rewriting before it counts.
  • Model-keyed packs have never matched real firmware. The lookup is proven against the live Dell, Lenovo and HP catalogs, but this is a Gigabyte board and no vendor publishes packs for it, so the match was driven by overriding what the firmware reports.
  • Lenovo's hash rests on a length match. The field is 64 hex characters so it is almost certainly SHA-256, but no 300MB Lenovo pack was ever downloaded and hashed end to end. Dell's was.
  • The certificate is self-signed. Windows will say the publisher is unknown, and that warning is correct. Antivirus reputation - the reason this left Python at all - stays unmeasured until a real certificate signs it.

Built with

C# on .NET 8, compiled ahead of time with Native AOT so the command line is a single signed executable with no runtime to install. Device access is CfgMgr32 and SMBIOS through direct P/Invoke; installs go through pnputil and nothing else. The window is WPF on the same engine the CLI uses, built from one factory so the two cannot drift. Vendor catalogs are parsed with the standard library only. Packaging is WiX 5, deliberately not 6, which would mean accepting a maintenance-fee licence. Tests are xUnit against fixtures trimmed from real vendor catalogs, so continuous integration never depends on Dell's servers being up.

It began as Python with a Qt front end. That version is preserved on a reference branch and is not maintained. The reason for leaving is in ADR-0001, along with the places where the rewrite deliberately behaves differently from the original.
